## Five ranked improvements

Ranked on user impact/risk, evidence confidence and effort. A later research sweep on main added dependency evidence; the report was refreshed against the newer main SHA. Validation work is ranked where it gates a costly or safety-sensitive decision. The five proposals preserve plan versus performed record, self-paced calendar-free Protocols, typed Load/Quantity and read-time projections.

### 1. Close the credential incident — security risk, high confidence, S/M

**Problem:** previously tracked authentication material could retain access or exist on a retained ref. **Evidence:** [incident checklist](../../security/incidents/2026-09-25-codex-tool-state.md) has unchecked provider revocation, retained-tip, native scanning and dummy-secret rejection tasks; current [Gitleaks run](https://github.com/pierrickmartino/workout-manager/actions/runs/37230268650) passes. **Status:** **partially shipped**, credential validity **unverified**. **Solution:** owner verifies provider revocation without recording values, audits retained branch tips, enables native secret scanning/push protection and records a rejected official dummy-secret push. **Benefit:** resolves account and privacy exposure instead of relying solely on file deletion. **Effort:** S if checks pass, M if ref remediation is needed. **Confidence:** high that closure evidence is absent; credential validity unknown. **Success:** all four dated, value-free closure items checked. **Tracking:** existing [incident record](../../security/incidents/2026-09-25-codex-tool-state.md); no duplicate issue.

### 2. Bring dependency floors onto supported patched versions — availability/security risk, high confidence, S

**Problem:** the exact web pin cannot receive security fixes on its current line, and permissive Python minimums permit vulnerable versions in a future constrained resolve. **Evidence:** [web manifest](../../../apps/web/package.json) pins Next.js 16.2.12, within the published affected ranges for [AVIF image optimization](https://github.com/advisories/GHSA-2xp9-vwfh-vxw4) and [next/og](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j); [API floors](../../../apps/api/pyproject.toml) allow PyJWT 2.9 and python-multipart 0.0.12, below patched versions cited in [PyJWT](https://github.com/advisories/GHSA-w6j9-cwv2-h6wq) and [multipart](https://github.com/advisories/GHSA-pp6c-gr5w-3c5g) advisories. The [5 October research sweep](https://github.com/pierrickmartino/workout-manager/blob/main/docs/research/2026-10-05.md) reports a fresh Python resolve selected patched versions. **Status:** **partially shipped** dependency hygiene; app exploitability **unverified** and the cited next/og path was not found used in current source. **Solution:** update Next.js to a current patched 16.3 release with its lockfile, raise the two Python minimums to patched releases, run web/API suites plus a focused upload/auth boundary check, and establish a reviewable update cadence. Do not treat advisory severity as proof of an app-level exploit. **Benefit:** future builds cannot silently retain known vulnerable minimums and the web app receives upstream fixes. **Effort:** S for pins/floors and validation; M if the upgrade breaks behavior. **Confidence:** high on versions and advisory ranges, medium on operational exposure. **Success:** lockfile audit has no applicable critical Next.js finding, Python minimum-version audit passes for these packages, and CI plus upload/auth checks pass. **New issue draft:** “Upgrade Next.js and raise security dependency floors.” Acceptance: pin a patched Next.js 16.3 release, raise PyJWT/python-multipart floors above cited affected ranges, document route applicability, and show clean audits and tests.

### 3. Handle Calibration transport ambiguity — workout trust, medium confidence, S

**Problem:** if a user taps Easier/Harder and the connection fails after the server commits, the control can leave an unhandled rejected promise and the user cannot tell which pitch is saved. **Evidence:** [control](../../../apps/web/components/pulse/calibration-control.tsx) awaits the server action and handles unsuccessful envelopes but contains no catch; [action](../../../apps/web/app/dashboard/calibration-actions.ts) calls [apiSend](../../../apps/web/lib/api.ts), whose fetch/JSON failures reject. The [absolute target](../../../apps/web/lib/calibration-control.ts) makes a retry idempotent. This is a **source-backed failure hypothesis**, not a reproduced lost-acknowledgement incident. **Status:** **partially shipped** error feedback. **Solution:** catch transport exceptions, present “could not confirm” with a retry/refresh, re-read canonical Calibration before asserting success, retain the absolute target. Do not rewrite a performed Session. **Benefit:** no silent uncertainty over what future Sessions prescribe. **Effort:** S. **Confidence:** medium pending a fault-injection run. **Success:** injected pre-commit failure and post-commit lost acknowledgement both produce a clear state and a retry converges to exactly one saved target without double stepping. **New issue draft:** “Reconcile Calibration after an uncertain network result.” Acceptance: the two fault paths, canonical refresh, accessible error/status and idempotent retry are tested.

### 4. Validate the installed workout recovery path — high impact/risk, medium confidence, M

**Problem:** the app promises a recoverable Live Session and queued Finish, but a gym-floor network outage or account switch may expose an untested gap. **Evidence:** [ADR-0059](../../adr/0059-account-scope-the-live-session-slot-and-finish-outbox.md), [ADR-0060](../../adr/0060-a-finish-is-an-immediately-real-logged-session-via-an-idempotent-outbox.md), [network-only service worker](../../../apps/web/public/sw.js) and the [prior isolated resilience report](../../development/ui-resilience-validation.md). These prove design and fixture behavior, not an installed authenticated phone. **Status:** **partially shipped**, real-device reliability **unverified**. **Solution:** use disposable accounts on installed iOS Safari and Android Chrome: start online, log offline, reload/update, finish during a failed request, switch account, restore connectivity, inspect one owner-scoped Logged Session and clear sync feedback; log browser versions and failures. If offline cold-start is essential to users, explicitly revisit ADR-0028/0061 with an owner decision on private cache isolation and server-derived projections before building it. **Benefit:** establishes whether the central workout can be trusted under common connectivity changes. **Effort:** M. **Confidence:** medium that the validation is valuable; defect rate unknown. **Success:** both device matrices complete with zero cross-account recovery and exactly one Logged Session per finish key; any failed case has a reproducible issue. **New issue draft:** “Run authenticated installed-PWA Live and Finish recovery matrix.” Acceptance: the scenarios, browser versions, sync states and account isolation above are recorded; no feature is claimed fixed merely because a fixture passed.

### 5. Make AI spend and failure visible to the operator — cost/safety risk, medium confidence, M

**Problem:** without verified production measurement, one cannot prioritize AI latency, failed calls or cache economics. **Evidence:** existing [#270](https://github.com/pierrickmartino/workout-manager/issues/270) defines the self-hosted recorder, cost, latency, failure, retention and erasure work; [ADR-0039](../../adr/0039-ai-usage-monitoring-via-self-hosted-langfuse.md) sets the design; current CI does not prove deployed dashboards. **Status:** **decided but operational completion unverified** (source may contain partial instrumentation; do not equate issue-open with feature absence). **Solution:** reconcile #270 acceptance against production configuration and a redacted end-to-end trace, then finish missing recorder/flush/retention/erasure steps there. Keep sensitive prompts in the approved self-hosted boundary. **Benefit:** cost and failure decisions can use measured provider calls. **Effort:** M. **Confidence:** medium until deployment evidence is available. **Success:** for one sampled week, metered calls, cache misses, p95 latency, failure rate and cost per generator kind reconcile, with 90-day retention and user erasure verified. **Tracking:** [#270](https://github.com/pierrickmartino/workout-manager/issues/270); no duplicate issue.

## One question before building

When a user changes the Protocol pitch, can they predict which of Load, Quantity, sets, rest and Target Effort will move, and do they trust the resulting Next Session? Observe a few strength and non-strength users and inspect actual re-pitch/undo rates before adding a preview or changing the calibrated rule. This is a **hypothesis** about comprehension, not an observed complaint.
