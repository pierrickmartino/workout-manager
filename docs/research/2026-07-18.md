# Research Report — 2026-07-18

Weekly research sweep for **workout-manager**: stack currency, security
advisories affecting our dependencies, UX patterns for the visual Protocol
Builder, and implementation references for the open AI-ready issue. No source
code, ADRs, or `CONTEXT.md` were touched in producing this report.

## Executive Summary

- **Two security advisories directly hit our stack and are the headline items.**
  1. **Clerk middleware bypass — CVE-2026-41248 (CVSS 9.1, Critical).** Affects
     `@clerk/nextjs`, which we pin at `^6.0.0`. Crafted requests can bypass
     `middleware` route protection and reach downstream handlers unauthenticated.
     Fixed in `@clerk/nextjs` **6.39.2** (6.x line). This is our auth seam — it
     warrants a prompt dependency bump and verification.
  2. **Starlette "BadHost" — CVE-2026-48710 (High).** FastAPI rides on Starlette;
     a malformed `Host` header can desync `request.url.path` from the dispatched
     route, enabling host-validation / auth-gate bypass. Fixed in **Starlette
     1.0.1** (2026-05-21). We don't pin Starlette directly — it comes transitively
     via `fastapi>=0.115`, so the floor must be raised through FastAPI.
- **Next.js + React coordinated security release (May 2026)** patched 13
  advisories (DoS, middleware/proxy bypass, SSRF, cache poisoning, XSS). Fixed in
  **Next.js 16.2.6** (and 15.5.18). We pin `next` at `^16.0.0`, so a lockfile that
  resolved before early May could still be on a vulnerable 16.0.x/16.1.x.
- **Stack is broadly current** but a minor-version behind in several places:
  latest are Next.js 16.2.x (16.3 in preview), React 19.2.7, Tailwind 4.3.1,
  FastAPI 0.139.2, SQLModel (2026-06-25 release), Alembic 1.18.5, RQ 2.10.0.
  None of these are breaking for us; the security-driven bumps are what matter.
- **The only open AI-ready issue, #146 (single HTTP transport seam), is already
  implemented and merged.** `lib/api.ts` + `lib/api.test.ts` exist, all eleven
  domain modules delegate to the seam, and ADR-0022 is in the tree
  (commits `504d173`, `be20e61`). No implementation work remains — see Findings.
- **Visual workout-builder UX research** reinforces our existing model: the
  un-performed-tail edit rule (ADR-0020), typed `Load` (ADR-0010), and the
  self-paced/calendar-free stance (ADR-0001) all line up with current best
  practice, with a few honest-model-compatible refinements worth considering
  (superset grouping, reorder affordances, per-set type). No calendar/mesocycle
  or "recovery %" patterns — those conflict with our invariants.

## Security Risks

Ranked by exposure to our current pins.

### 1. CRITICAL — Clerk middleware route-protection bypass (CVE-2026-41248)
- **Our exposure:** `apps/web/package.json` pins `@clerk/nextjs` `^6.0.0`. Clerk
  is our entire auth boundary; the web app fetches server-side with a Clerk JWT
  that the FastAPI backend verifies. A middleware bypass is a direct
  authorization risk.
- **Nature:** Crafted requests bypass `middleware` gating and reach downstream
  handlers without authentication. CVSS **9.1**.
- **Fix:** upgrade to `@clerk/nextjs` **6.39.2** (patched line for 6.x; 5.7.6 and
  7.2.1 patch the other majors). `@clerk/shared` patched at 3.47.4 / 4.8.1.
- **Recommended action:** bump the pin and re-run the auth flow. Because it's a
  middleware-layer bypass, also sanity-check that no protected route relies on
  middleware *alone* — our server components independently attach + verify the
  JWT, which is a mitigating second gate worth confirming.

### 2. HIGH — Starlette "BadHost" host-header auth bypass (CVE-2026-48710)
- **Our exposure:** transitive via `fastapi>=0.115` (FastAPI is built on
  Starlette). Any Starlette `<= 1.0.0` is affected.
- **Nature:** a `Host` header containing `/`, `?`, or `#` desyncs
  `request.url.path` from the router-dispatched path, enabling host-validation /
  auth-gate bypass. Rated Moderate–High (6.5–7.0).
- **Fix:** **Starlette 1.0.1** (2026-05-21). Raise the floor by bumping FastAPI to
  a release that requires Starlette ≥ 1.0.1, then confirm the resolved Starlette
  version in the lockfile/venv.
- **Recommended action:** verify `starlette>=1.0.1` resolves after the FastAPI
  bump; our host validation isn't custom, so the framework fix is the remedy.

### 3. HIGH — Next.js / React coordinated security release (May 2026)
- **Our exposure:** `next` pinned `^16.0.0`; `react`/`react-dom` `^19.0.0`. 13
  advisories across DoS, middleware/proxy bypass, SSRF, cache poisoning, XSS; one
  in React Server Components.
- **Fix:** **Next.js 16.2.6** (also 15.5.18); React fix in the RSC patch line
  (19.x maintenance). A caret pin permits these, but a lockfile resolved before
  ~2026-05-06 may still sit on a vulnerable 16.0.x/16.1.x.
- **Recommended action:** run `npm audit` / refresh the lockfile so `next`
  resolves to **≥ 16.2.6** and React to a post-Dec-2025 patched 19.x.

### Transport-seam pattern (for reviewers of #146, already-built)
- `server-only` package: build-time guard that a module never enters the client
  bundle — the mechanism keeping JWT-attach server-side.
- Typed `fetch` wrapper patterns for the App Router: centralizing base-URL, auth
  attach, and cache policy in one server module is the established best practice,
  matching what ADR-0022 already did.

### Visual workout builder UX (for a future Builder issue)
Current best practice for programming/builder UIs, filtered to what's compatible
with our honest, self-paced model:

- **Direct-manipulation reorder** (drag-and-drop) for arranging exercises/sets is
  the expected affordance for "build and rearrange visually instead of editing a
  spreadsheet." Compatible with ADR-0020 **only** if drag/reorder is restricted to
  the **un-performed tail** — a performed Session is settled record and must not
  be reorderable.
- **Per-set granularity:** sets, set *type*, rest, target reps/rep-range, and load
  are the standard editable variables. Maps cleanly onto our typed `Load`
  (ADR-0010) — keep load as a typed value (absolute / bodyweight / %1RM /
  qualitative / range), never a bare kg number, even in the builder UI.
- **Superset / grouping** with A/B/C badges and auto-advance to the next member is
  a widely adopted pattern worth considering for the Builder and Live Session.
- **Fast time-to-first-workout** (get a user into their first session in ~60s;
  simplified onboarding can lift retention ~50%) supports keeping the Builder's
  default path short.
- **Adaptive UI** per session type (build vs. log vs. review) is a 2026 mobile
  trend that aligns with our distinct Builder / Live / Analytics surfaces.
- **Deliberately excluded as invariant-violating:** calendar/dated mesocycle
  scheduling, "recovery %," and daily-streak mechanics. These are common in
  competitor builders but conflict with ADR-0001 (self-paced, calendar-free) and
  our read-time-projection rule (ADR-0018/0019). Readiness stays a 3-state signal,
  not a score.
