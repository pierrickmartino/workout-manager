## Security Risks

Ordered by live severity. Items 1–2 are **actionable this cycle**; item 3 is a
now-patched advisory kept as a review guardrail; item 4 is a carried-forward PWA
hardening item, now bounded by the ADRs we shipped.

### 1. HIGH — `next@16.2.9` in the lockfile is below the July-2026 patch line
- **Our exposure (concrete):** `apps/web/package-lock.json` resolves **16.2.9**;
  the **July 2026 Next.js security release** (2026-07-21) fixes **9 CVEs** at
  **16.2.11**. Highest-relevance items for us:
  - **CVE-2026-64642 (CVSS 8.3) — middleware/proxy bypass**, App Router built with
    **Turbopack** + a **single** `config.i18n.locales` entry. Any auth/security
    check performed in middleware can be skipped. **This is our auth gate** — our
    `dev`/`dev:turbo` scripts use webpack/turbopack respectively, so verify the
    build config against the trigger condition.
  - **CVE-2026-64645 (CVSS 8.3) — SSRF/open-redirect** where a `rewrites()`/
    `redirects()` destination hostname is built from request-controlled input.
  - **CVE-2026-64649 — SSRF** affecting Server Actions on custom servers.
  - **CVE-2026-64641 (CVSS 8.2) — Server Actions DoS.** Plus Medium
    cache-confusion / internal-endpoint-disclosure issues.
- **Action:** `npm update next` to **≥ 16.2.11**, commit the lockfile, re-run the
  web suite. The pin already allows it — this is purely a resolved-version drift.

### 2. HIGH — Starlette pin floor (`>=1.0.1`) no longer covers the newest host-desync variant
- **Our exposure:** `pyproject.toml` pins `starlette>=1.0.1` *directly* (a
  deliberate, commented choice for the BadHost CVE-2026-48710). Two newer
  advisories sit above that floor:
  - **CVE-2026-54282 — path host poisoning.** An unvalidated request path is
    concatenated into `{scheme}://{host}{path}` and re-parsed; a path not
    beginning with `/` (e.g. `@evil.com`) moves the authority boundary, so
    `request.url.hostname`/`netloc` become **attacker-controlled**. This is the
    **same host-validation-bypass class** the pin was added to defend against.
    **Fixed in 1.3.0.**
  - **CVE-2026-54283 — form-limit-bypass DoS.** `request.form()`'s `max_fields` /
    `max_part_size` limits are enforced for multipart but **silently ignored for
    `application/x-www-form-urlencoded`**, so an unauthenticated caller can send an
    oversized/high-cardinality urlencoded body. **Fixed in 1.3.1.**
- **Why it matters despite no lockfile:** with no `uv.lock`/`requirements.txt`
  pinned in the tree, a fresh CI/Docker install *today* pulls ≥ 1.3.1 (safe) — but
  the floor and its comment now **misstate the guarantee**, and any transitive
  cap or a future lockfile could silently land a vulnerable 1.0.x–1.2.x.
- **Action:** raise the direct pin to **`starlette>=1.3.1`** and update the
  comment to name 54282/54283. Consistent with the project's existing pattern of
  pinning Starlette directly for security.

### 3. LOW (patched) — Clerk combined-predicate authorization footgun (CVE-2026-42349)
- **Status:** **not exposed** — `@clerk/nextjs` resolves to **6.39.5**, above the
  fix at **6.39.3** (CVSS 7.6) and the earlier critical **6.39.2** fix
  (CVE-2026-41248). Close the Clerk advisory thread from prior reports.
- **Residual guardrail (code-review, not a bump):** CVE-2026-42349's class is a
  **combined-predicate bug** — a single `has()` / `auth.protect()` call that
  combines a *reverification* check with a role/permission/feature/plan check (or
  a billing check with a role/permission check) evaluated to `true` when only one
  component passed. The SDK is fixed, but the durable habit is to **split combined
  checks into sequential single-condition checks** and deny if any fails. Worth a
  one-line review note wherever auth predicates gate protected routes.

### 4. MEDIUM — Service-worker cache versioning / stale-shell hygiene (carried, now bounded)
- **Our exposure, re-scoped:** ADR-0028 already forbids caching authenticated
  navigation and ADR-0036 makes a nonce CSP the DOM-XSS front line — so the
  cross-user stale-auth and injected-script vectors from 07-21 are now
  architecturally addressed. The residual is the **operational** footgun the 2026
  PWA literature flags as the #1 regression: an **SW update that ships a stale or
  broken cache** — passing in DevTools with caches cleared, failing on a real
  device holding a prior-version cache.
- **Action:** if/when the ADR-0028 service worker lands, adopt **Workbox** for
  lifecycle management, enforce **cache versioning + namespace isolation**, keep
  authed `/api/*` on Network-First/uncached (ADR-0022 `cache: "no-store"` seam),
  and **gate every release** on an SW test run **on a real device with a real
  stale cache**, not just DevTools.

### Market positioning (competitor gaps → our wedge)
- **The recovery loop is still open — and the market says so.** Across 2026
  reviews, **no** major logger (Hevy, Strong, Fitbod, Jefit, Freeletics) reads
  HRV/sleep/RHR to rewrite *today's* session. Where marketing claims otherwise,
  independent reviews contradict it. The field's own recommendation —
  *"the best 2026 setup isn't one app, it's a stack"* (logger + wearable) —
  concedes the loop is unclosed. Our ADR-0001/0008 stance is the deliberate fork

- **Fragmentation by modality is accelerating.** A hypertrophy specialist
  (**Alpha Progression**, RIR-based) is now a named 2026 pick alongside Fitbod
  (strength-leaning), Hevy (logging/community), and Freeletics (HIIT). Each owns
  one modality well and the others thinly. Our **type-neutral spine**
  (strength/cardio/hiit/yoga/mobility with type-neutral XP/Achievements and typed
  `Load`, ADR-0010/0018) answers the fragmentation with **one honest engine** — a
  wedge that is *narrative, not capability*.
- **Pricing spread persists** (~$24/yr Hevy free-forever log vs ~$96/yr Fitbod
  trial-grade free). Because our gamification is read-time projection, an
  unlimited honest free log imposes no storage-ledger cost — a generosity posture

### Visual workout-builder UX (for the ADR-0023 + ADR-0027 manipulation layer)
- **Accessible reordering pattern (validates ADR-0027's button floor):** per-item
  **up/down move buttons** that move one position and **keep focus with the
  moved item**, so TalkBack/VoiceOver/keyboard users don't lose their place. Build
  drag **on top of** this floor, not instead of it.
- **Touch:** touch-friendly **drag handles** (not whole-row press-and-hold);
  generous drop-zone hit areas (~1cm); **avoid vertical drag that conflicts with
  native scroll** — the exact hazard for a phone-primary vertical exercise list.
- **Superset grouping:** one-action group-into-container is the established
  pattern; ADR-0023's round-major overlay should read as a visible container.
- **dnd-kit fit:** deliberately **not** built on the HTML5 DnD API (which has no
  touch/keyboard support); ships default ARIA, live-region announcements, and
  arrow/enter/escape keyboard dragging — matching ADR-0027's accessibility bar for
  React 19.

### PWA UX best practices (for `apps/web`, ADR-0028 / ADR-0036 in force)
- **Three non-negotiables:** service worker + Web App Manifest + HTTPS. Miss one
  and installability is silently suppressed. Run the PWA testing checklist
  **before every major release and after every SW change.**
- **Caching strategy (Workbox-managed):** Cache-First for static assets,
  Network-First for API freshness, Stale-While-Revalidate for non-critical
  assets — with authed `/api/*` staying uncached (ADR-0022/0028).
- **The regression to gate on:** an SW update that breaks offline **on a real
  device with a prior-version cache** while passing in DevTools. Test on a real
  device with real stale cache; monitor SW install rates + cache-hit ratios.
- **iOS reality:** SWs cache for offline but **cannot run background tasks** —
  cache critical assets at install; our finish-only server-persistence boundary
  (ADR-0012/0035) already aligns with "no Background Sync."
- **Perceived performance:** show cached data immediately with a sync-status cue;
  skeletons over spinners; tie changes to LCP/INP/CLS budgets on a throttled
  low-end Android.

## Questions

1. **Wearable/recovery posture — the headline strategic call (carried forward,
   sharper).** The market now openly recommends a *two-device stack* because no
   single app closes the recovery loop. Do we (a) **hold the honest self-paced
   line** and market *that* against the "loggers, not coaches / bring your own
   wearable" field, or (b) open a **bounded, invariant-respecting lane** where an
   optional wearable signal *only* informs the existing 3-state **Readiness** (no
   recovery %, no dated schedule, no "today")? Deserves a grill session + ADR
   before any issue.
2. **Do we compete on freemium generosity, and do we say it?** The ~4x price
   spread and Fitbod's trial-grade free tier remain an opening; unlimited honest
   logging costs us no stored ledger. In scope for the FO1 positioning slice
   (F-D), or out for now?
3. **Type-neutral positioning — narrate the wedge now that the field is
   fragmenting by modality?** Alpha Progression (hypertrophy), Freeletics (HIIT),
   Fitbod (strength) each own one lane thinly; our one honest type-neutral engine
   is the counter. Ship the FO1 copy that actually *says* "trains every modality
   honestly," or leave it implicit?
4. **Does dependency hygiene run on a cadence?** This cycle surfaced a lockfile
   that drifted below a published patch (Next.js) and a direct pin whose comment
   went stale (Starlette). Do we want a **scheduled `chore(deps)` + advisory
   sweep** (e.g. Dependabot/renovate or a recurring task) so security drift is
   caught mechanically rather than by the weekly research report?
5. **Builder manipulation scope (ADR-0023 + ADR-0027).** Confirm the first cut
   ships **both** drag-to-reorder and drag-to-group supersets with the button
   floor + touch/keyboard parity as acceptance criteria — or reorder first,
   grouping second? The accessibility floor is the same either way.
