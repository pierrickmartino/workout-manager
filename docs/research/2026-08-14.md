## Executive Summary

  against three 2026 CVEs.** `apps/api/pyproject.toml` pins `pyjwt[crypto]>=2.9`;
  three PyJWT advisories now sit above that floor — **CVE-2026-48526** (HIGH,
  CVSS 7.4: a public-key JWK accepted as an HMAC secret → forged HS256 tokens,
  fixed **2.13.0**), **CVE-2026-32597** (HIGH: unknown `crit` header extensions

### F-A · #270 — Langfuse AI-usage monitoring (ready-for-agent; a stack-currency note attaches)

**State:** open, `ready-for-agent`; implements **ADR-0039** (operational
AI-usage monitoring via self-hosted Langfuse). The `langfuse>=2.0,<3` pin and its
comment in `pyproject.toml` already document *why* it targets v2 (the production
`LangfuseGenerationCallRecorder` speaks the low-level v2 client API —
`client.trace(...)` → `.generation(...)`, `client.flush()` — which the v3
OTel-based rewrite removed).

**Research note for whoever picks this up:** Langfuse has since moved past v3 to
**v4 (latest 4.14.4, the OTel-native line)**. This does **not** block #270 — the
v2 pin is deliberate and the recorder is imported lazily so the offline suite
never touches it. But two things are worth stating in the PR:
- The pin is now **two majors behind** upstream, not one. Bumping is a **recorder
  rewrite** (v2 low-level client → OTel spans), not a version bump — the ADR-0039
  comment should be read as still-accurate but with "v3" generalised to "v3+/v4".
- The OTel line has a known **cost footgun**: once instrumented, Langfuse can
  capture unrelated OTel spans (DB/HTTP/framework), inflating trace volume. If a
  future v4 migration is ever scoped, it must scope span capture to LLM calls
  only — matching the recorder's current one-generation-per-call shape.

### F-B · Builder manipulation layer (ADR-0023 + ADR-0027 decided; now a WCAG conformance line)

**State:** decided (supersets as a round-major grouping overlay, ADR-0023;
`@dnd-kit` over a **keyboard-accessible button floor**, ADR-0027; suppressed for
Sensitive-Constraint users via a shared validator). **Not yet built.**

This cycle's sources harden ADR-0027 from "good practice" to "conformance":
- **The button floor is a WCAG 2.5.1 requirement.** 2026 accessible-DnD guidance
  now cites **WCAG 2.5.1 Pointer Gestures** directly: any drag-based interaction
  **must** ship a single-pointer (non-drag) alternative. ADR-0027's per-item
  up/down move buttons *are* that alternative — build them as the baseline, not a
  fallback, and they double as the keyboard and screen-reader path.
- **Keyboard grammar is settled:** space to pick up, arrow keys to move, space to
  drop, escape to cancel — exactly `@dnd-kit`'s default keyboard sensor. Pair
  with a **live region** announcing "picked up / moved to position N / dropped."
- **Touch:** touch-friendly **drag handles** (not whole-row press-and-hold),
  enlarged drag/drop hit areas on crowded/nested lists, and **avoid vertical drag
  that fights native scroll** — the exact hazard for a phone-primary vertical
  exercise list.
- **Invariant-safe:** every gesture stays inside ADR-0020's **un-performed tail**;
  the client drag layer reads the frozen performed prefix and refuses drops into
  it, mirroring the server `deploy_validation.py` gate; superset suppression for
  Sensitive-Constraint users enforced in the shared validator (ADR-0003 posture).

## Security Risks

Ordered by live severity. Item 1 is **actionable this cycle** (low urgency —
defense-in-depth, not a live exploit); items 2–3 are confirmed-closed threads
kept for the record; item 4 is a carried-forward PWA hardening item bounded by
shipped ADRs.

### 1. LOW–MEDIUM — `pyjwt[crypto]>=2.9` floor is stale against three 2026 PyJWT CVEs

- **Our exposure (concrete, and mostly benign):** `apps/api/pyproject.toml` pins
  `pyjwt[crypto]>=2.9`. Three PyJWT advisories now sit above that floor:
  - **CVE-2026-48526 (HIGH, CVSS 7.4) — algorithm-confusion HS256 forgery.** A
    verifier that allows **both** an asymmetric and an HMAC algorithm in
    `algorithms=[…]` *and* passes a **raw-JSON JWK** as `key=` will accept the
    issuer's public key as the HMAC secret, letting an attacker forge tokens.
    **Not exposed:** `app/auth/jwks.py` decodes with `algorithms=["RS256"]`
    (single, asymmetric) and passes a parsed `PyJWK.key`, not raw JSON — neither
    precondition holds. Fixed in **2.13.0**.
  - **CVE-2026-48524 — PyJWKClient JWKS-flood / cache behavior.** Affects
    `PyJWKClient`, which re-requests the JWKS for every unknown `kid`.
    **Not exposed:** `app/auth/jwks_provider.py` fetches and TTL-caches the JWKS
    itself over `httpx` and matches `kid` via `PyJWKSet.from_dict`; it does not
    use `PyJWKClient`. Fixed in **2.13.0**.
  - **CVE-2026-32597 (HIGH) — unknown `crit` header extensions accepted.** PyJWT
    < 2.12.0 accepted JWS tokens declaring unknown critical (`crit`) header
    params, which RFC 7515 says must invalidate the token. **Weakly exposed:**
    our `jwt.decode` sets no `crit` handling, so on a pre-2.12 resolve a Clerk
    token carrying an unknown `crit` would be accepted rather than rejected — a
    spec-compliance gap, low practical severity for an RS256-only issuer. Fixed
    in **2.12.0**.
- **Why it matters despite the benign usage:** with **no `uv.lock`/`requirements.txt`
  in the tree**, a fresh CI/Docker install *today* resolves ≥ 2.13.0 (safe) — but
  the `>=2.9` floor **permits** a vulnerable 2.9–2.11, has **no explanatory
  comment**, and any future lockfile or transitive cap could silently land one.
  This is the identical failure mode we just fixed for Starlette.
- **Action:** raise the direct pin to **`pyjwt[crypto]>=2.13.0`** and add a
  security comment naming CVE-2026-48526 / -48524 / -32597 — consistent with the
  project's existing pattern of pinning security-relevant floors directly
  (Starlette). Low urgency, single-line change; re-run the API suite to confirm
  the auth tests still pass under the raised floor.

### 2. RESOLVED (07-29 / PR #260) — Next.js July-2026 CVEs and Starlette host-desync

- **Confirmed landed in-tree.** `apps/web/package-lock.json` resolves **`next`
  16.2.12** (≥ the 16.2.11 line that fixes the 9-CVE July release: CVE-2026-64642
  middleware/proxy bypass, -64645/-64649 SSRF, -64641 Server Actions DoS);
  `apps/api/pyproject.toml` pins **`starlette>=1.3.1`** with the
  48710/54282/54283 comment. No August successor release to Next.js's July
  security drop was found — search hits describing an "August release" are
  re-summaries of the same July CVEs. Nothing to redo.

### 3. RESOLVED (patched) — Clerk advisories (CVE-2026-41248 + -42349)

- **Confirmed patched:** `@clerk/nextjs` resolves **6.39.5**, above the critical
  middleware-bypass fix (6.39.2 / CVE-2026-41248, CVSS 9.1) and the
  authorization-bypass fix (6.39.3 / CVE-2026-42349). **Residual guardrail
  (code-review, not a bump), carried from 07-29:** never combine a reverification
  check with a role/permission/billing check in a single `has()` /
  `auth.protect()` call — split into sequential single-condition checks. The SDK
  is fixed; this is durable habit.

### 4. MEDIUM — Service-worker cache versioning / stale-shell hygiene (carried, bounded)

- **Re-scoped as before.** ADR-0028 forbids caching authenticated navigation and
  ADR-0036 makes a nonce CSP the DOM-XSS front line, so the cross-user stale-auth
  and injected-script vectors are architecturally addressed. The residual is the
  **operational** footgun the 2026 PWA literature keeps flagging: an SW update
  that ships a stale/broken cache — passing in DevTools with caches cleared,
  failing on a real device holding a prior-version cache.
- **Action (when the ADR-0028 SW lands):** adopt **Workbox** for lifecycle
  management, enforce cache versioning + namespace isolation, keep authed
  `/api/*` on Network-First/uncached (ADR-0022 `cache: "no-store"` seam), and
  **gate every release on an SW test run on a real device with a real stale
  cache**, not just DevTools.

### Market positioning (competitor gaps → our wedge)
- **The recovery loop is no longer un-closed — one competitor now closes it.**
  Across 2026 reviews, **SensAI** is named as the app that reads HRV/sleep/RHR
  daily via HealthKit and **rewrites today's session** — an LLM coach with
  cross-session memory of injuries/constraints — with reviewers citing an
  HRV-guided-training meta-analysis (VO2max effect size ~0.40) as evidence. The
  mainstream loggers (Hevy, Fitbod, Strong, Jefit) still **do not** read wearable
  recovery into programming. Our ADR-0001/0008 stance (self-paced, calendar-free,
  3-state Readiness, no recovery %, no "today") is the deliberate fork — but the
  fork now has a named occupant on the other side (see Q1).
- **Fragmentation by modality continues.** Fitbod (strength), Hevy
  (logging/community), Freeletics (HIIT), Alpha Progression (hypertrophy/RIR),
  SensAI (wearable-coach) each own one lane well and the others thinly. Our
  **type-neutral spine** (strength/cardio/hiit/yoga/mobility with type-neutral
  XP/Achievements and typed `Load`, ADR-0010/0018) answers the fragmentation with
  **one honest engine** — a wedge that is *narrative, not capability*.
- **Pricing spread persists** (~$24/yr Hevy free-forever log vs ~$96/yr Fitbod

### Visual workout-builder UX (for the ADR-0023 + ADR-0027 manipulation layer)
- **WCAG 2.5.1 makes the button floor mandatory:** every drag interaction needs a
  single-pointer, non-drag alternative. ADR-0027's per-item up/down move buttons
  are exactly that — build them as the baseline that also serves keyboard and
  screen-reader users, not as a fallback.
- **Keyboard grammar:** space pick-up / arrow move / space drop / escape cancel —
  `@dnd-kit`'s default keyboard sensor — with a **live region** announcing
  "picked up / moved to position N / dropped."
- **Touch:** touch-friendly **drag handles** (not whole-row press-and-hold),
  enlarged hit areas on crowded/nested lists, **avoid vertical drag that fights
  native scroll**.
- **Superset grouping:** one-action group-into-container is the established
  pattern; ADR-0023's round-major overlay should read as a visible container the
  user groups members into.
- **dnd-kit fit:** deliberately not built on the HTML5 DnD API (no touch/keyboard);
  ships default ARIA, live-region announcements, and arrow/enter/escape keyboard
  dragging — matching ADR-0027's accessibility bar for React 19.

### PWA UX best practices (for `apps/web`, ADR-0028 / ADR-0036 in force)
- **Three non-negotiables:** service worker + Web App Manifest + HTTPS. Miss one
  and installability is silently suppressed; run the PWA checklist before every
  major release and after every SW change.
- **Caching strategy (Workbox-managed):** Cache-First for static assets,
  Network-First for API freshness, Stale-While-Revalidate for non-critical
  assets — authed `/api/*` staying uncached (ADR-0022/0028).
- **The regression to gate on:** an SW update that breaks offline **on a real
  device with a prior-version cache** while passing in DevTools.
- **iOS reality:** SWs cache for offline but **cannot run background tasks** (no
  Background Sync) and there is **no automatic install prompt** (Share-menu only).
  Our finish-only server-persistence boundary (ADR-0012/0035) already aligns.
- **Perceived performance:** show cached data immediately with a sync-status cue;
  skeletons over spinners; tie changes to LCP/INP/CLS budgets on a throttled
  low-end Android.

## Questions

1. **Wearable/recovery posture — now with a named occupant on the other side
   (Q1, escalated).** The recovery loop the field said was un-closed now has a
   named app closing it (SensAI: HRV/sleep → today's session), with a
   meta-analytic evidence hook. Do we (a) **hold the honest self-paced line** and
   market *that* against the "coach that reads your wearable" pitch, or (b) open a
   **bounded, invariant-respecting lane** where an optional wearable signal *only*
   informs the existing 3-state **Readiness** (no recovery %, no dated schedule,
   no "today")? This is the headline strategic call — deserves a grill session +
   ADR before any issue.
2. **Do we bump PyJWT proactively or on cadence?** Security #1 is
   defense-in-depth (we're not concretely exposed), but it's the second stale
   floor surfaced by the weekly report in as many cycles. Ship the one-line
   `pyjwt>=2.13.0` bump now, or fold it into a decision on a **scheduled
   `chore(deps)` + advisory sweep** (Dependabot/renovate) so drift is caught
   mechanically? (Same open question as 07-29 Q4.)
3. **Do we compete on freemium generosity, and do we say it?** The ~4x price
   spread and Fitbod's trial-grade free tier remain an opening; unlimited honest
   logging costs us no stored ledger. In scope for the FO1 positioning slice
   (F-D), or out for now?
4. **Type-neutral positioning — narrate the wedge now that the field is
   fragmenting by modality?** Five named competitors each own one lane thinly;
   our one honest type-neutral engine is the counter. Ship FO1 copy that actually
   *says* "trains every modality honestly," or leave it implicit?
5. **Builder manipulation scope (ADR-0023 + ADR-0027).** Confirm the first cut
   ships **both** drag-to-reorder and drag-to-group supersets with the WCAG-2.5.1
   button floor + touch/keyboard parity as acceptance criteria — or reorder
   first, grouping second? The accessibility floor is the same either way.
