## Executive Summary

- **The universal market gap is unchanged and now stated bluntly by the
  reviewers: every major logger "tracks what you did, but none know how recovered
  you are right now."** Fitbod, Hevy, Strong, Jefit, and Freeletics all adjust on
  fatigue models, RPE, and completion — *not* on wearable recovery (HRV/sleep/RHR).
  This is the same recovery-aware coaching gap the 07-19 report flagged, and it
  remains the field's biggest opening. Our stance is the deliberate opposite
  (self-paced, calendar-free, no "today", **Readiness is a 3-state signal not a
  score** — ADR-0001/0008). It stays a **conscious strategic fork**, logged as the
  headline Question, not a Finding-to-fix.
- **A new, sharper competitor axis this cycle is price and freemium generosity —
  and it cuts in our favor if we choose to compete there.** Fitbod now lists at
  **$95.99/yr** with a free tier that is effectively a 7-day / 3-workout trial;
  Hevy is **$23.99/yr** and tracks unlimited workouts free forever — a ~4x premium
  gap. This reframes the wedge: our differentiator is not only *type-neutral
  honesty* but the chance to be **generous with the honest record** (everything
  gamified is a read-time projection, so an unlimited free log costs us no stored
  ledger). Nothing in the product currently *states* either the multi-modality or
  the data-ownership story.
- **Named competitor ceilings continue to line up with our invariants.** Hevy has
  a **smaller (~400) exercise library** and **logging-only** wearable integration
  (no recovery data flows into programming); Fitbod is strength-leaning with a thin
  progression system; Freeletics "works for HIIT but not strength/hypertrophy" and
  adapts only on RPE/completion. Our **type-neutral spine** (strength / cardio /
  hiit / yoga / mobility), AI-enriched catalog that stores invented movements once
  for everyone, honest typed `Load` (ADR-0010), and read-time PR/Progression engine
  answer these directly. The gap is **narrative, not capability**.
- **Visual-builder UX best practice tightened into hard numbers this cycle:**
  touch targets ≈ **1cm × 1cm**, **dotted/dashed drop-zone borders**, escalating
  per-state feedback, microcopy that *foreshadows* the drop, and an explicit
  **build-path decision** (native HTML DnD API vs library vs no-code) driven by the
  team's **accessibility** requirement. This is direct acceptance-criteria fuel for
  the already-decided ADR-0023 manipulation layer (drag-to-reorder + drag-to-group
  supersets), all of it staying inside the **un-performed tail** (ADR-0020).
- **PWA best practice has consolidated into a caching-strategy matrix and a
  measurement bar.** App shell = **Cache First**; API data = **Network First** with
  cache fallback; images = **Stale-While-Revalidate**; target **repeat-load LCP < 1s**
  once the shell is cached; tie changes to **INP/LCP/CLS budgets**; **skeleton
  screens over spinners**; run **Lighthouse's 13-point PWA audit every release**.
  The matrix maps cleanly onto our transport seam (ADR-0022, authed `/api/*` is
  `cache: "no-store"`) — but only if any future service worker keeps `/api/*` on
  Network First and never caches authed reads. **iOS remains the constraint**
  (no Background Sync, ~7-day storage eviction, EU standalone-PWA removal
  fragmenting the ecosystem).
- **No open issues on the tracker** (`list_issues` → 0). This is a research-only
  cycle; the inputs here are fuel for the next issues, chiefly the ADR-0023 Builder
  manipulation layer, the gamification/PR Home & Analytics fan-out, and the
  positioning/pricing narrative.

## Findings for Active Issues

The issue tracker currently has **zero open issues** (`list_issues` → 0), so there
is no `ready-for-agent` work to pick up. The "active" work in flight is the
already-decided-but-unbuilt set recorded in `docs/research/next-feature.md`,
`docs/pulse-feature-gap.md`, and ADR-0023. The findings below map this cycle's
research onto those.

### F-A · Builder manipulation layer (ADR-0023 decided; UX now has hard numbers)

**State:** decided (supersets as a round-major grouping overlay; AI generator emits
them; drag-to-reorder lands alongside drag-to-group; suppressed for
Sensitive-Constraint users via a shared validator). **Not yet built.**

This cycle's builder-UX sources turn the decision into concrete, testable
acceptance criteria:

- **Drag handles must be visually distinct** icons that stand apart from other UI,
  signalling "this moves" at a glance — not an ambient whole-row drag.
- **Touch targets ≈ 1cm × 1cm** of unused space, so the gesture works on the phone,
  which for a PWA gym app *is* the primary device.
- **Drop zones use dotted/dashed borders** and a clear structure so the eye finds
  where an item can land; the target intensifies as the dragged item nears.
- **Multi-zone feedback + microcopy foreshadowing.** With more than one drop target
  (reorder-within-Session vs group-into-Superset), each needs differentiated
  feedback and microcopy that previews the outcome (e.g. "release to group into a
  superset"). This is exactly the two-target case ADR-0023 introduces.
- **Choose the build path against the accessibility bar.** The four paths (native
  HTML Drag-and-Drop API, an open-source DnD library, no-code, custom) trade off on
  keyboard + touch parity. Keyboard operability is **non-negotiable** here (it is
  also required by the Accessibility pass in `next-feature.md`), so the choice
  should be made *for* accessibility, not retrofitted.
- **Constraint:** every gesture stays inside ADR-0020's **un-performed tail** — a
  performed Session is settled record and must never be draggable or reorderable.
  The client drag layer must read the frozen prefix and refuse drops into it,
  mirroring the server's `deploy_validation.py` gate.

### F-B · Gamification / PR fan-out to Home & Analytics (named, unbuilt)

**State:** the XP/Level/Streak/Achievement engine (ADR-0018/0019) and the
PR/1RM/volume engine (ADR-0010) are shipped and surfaced on Profile / Analytics /
Exercise Detail; the **Home + Analytics fan-out** is the named remaining slice.

Market relevance sharpened this cycle: with the field's differentiation stalled on
recovery data none of them own, **visible progress/momentum on the highest-traffic
surface (Home)** is the cheapest competitive win available. Surfacing
Level / XP / Streak and the top PR on Home — **off the same read-time endpoints, no
new domain** — directly answers the "feels generic after a few weeks" critique
levelled at Freeletics, and it costs no stored ledger (all projections). This is
capability wiring, the low-risk category the gap analyses keep pointing at.

### F-C · Positioning + freemium-generosity narrative (new this cycle)

**State:** the FO1 welcome/tagline and type-neutral messaging remain unbuilt
(`docs/pulse-feature-gap.md`); this cycle adds a **pricing/freemium** angle to it.

The competitor pricing spread (Fitbod ~$95.99/yr with a trial-grade free tier vs
Hevy ~$23.99/yr with unlimited free logging) exposes an un-narrated asset: because
XP, Streak, Achievements, and PRs are **read-time projections over the raw record**
(ADR-0018/0019), an *unlimited free log* imposes no storage-ledger cost on us and
loses no honesty. A positioning slice could state both the **multi-modality wedge**
("trains every modality honestly") and a **data-ownership/generosity posture**
(unlimited honest record, exportable — pairs with the Data Export item in
`next-feature.md`). Zero domain change; it makes existing invariants legible and
sellable.

## Security Risks

Scoped to this report's three topics (market / UX / PWA). The three dependency-bump
advisories from **2026-07-18** (Clerk 6.39.2, FastAPI → Starlette ≥ 1.0.1,
Next.js ≥ 16.2.6) remain the highest-severity items overall and are **carried
forward as Next Actions**, not repeated in detail here.

### 1. HIGH — Client-side Live Session storage is a confidentiality + integrity surface
- **Our exposure:** the Live Session persists to a single `localStorage` slot
  (ADR-0012). `localStorage` is **plain-text, same-origin, readable by any script
  on the page** with no expiry we control. Any XSS on `apps/web` can read a paused
  session or write a forged one the `ResumeSessionBanner` faithfully hydrates.
- **This cycle's added guidance:** 2026 PWA-security sources are explicit that
  sensitive client state should be **encrypted with the Web Crypto API before it
  touches localStorage/IndexedDB**, and that **Trusted Types** plus a strict CSP
  are the front-line DOM-XSS defense. Concretely for us: (a) treat the stored slot
  as **untrusted input on hydration** — schema-validate the shape on the resume
  path, never `JSON.parse`-and-trust; (b) keep **no secret/PII** in it (it holds
  low-sensitivity workout performance, but it is still user data); (c) evaluate
  **Trusted Types + `worker-src`** in the CSP so an injected script can neither
  execute in a service-worker context nor trivially exfiltrate the slot.

### 2. MEDIUM — Service-worker cache poisoning / cross-user stale-auth
- **Our exposure:** a service worker's value is a cache, but a mis-scoped cache is a
  classic footgun — caching an **authenticated** response and later serving it to a
  different session, or pinning a stale/vulnerable app-shell past a security
  release. This intersects the still-open Next.js cache-poisoning advisory.
- **This cycle's added guidance:** the 2026 literature (and the academic *"The
  Remote on the Local"* study of service-worker cache attacks) converges on
  **validate-before-cache**, **cache versioning**, and **cache namespace
  isolation** so one context's entries can't be served to another. For us that
  means: if/when a service worker is added, keep **authed `/api/*` reads on
  Network First (never cached)** — aligning with ADR-0022's `cache: "no-store"`
  seam — and **cache-first only versioned static shell/assets**. Never cache a
  response carrying the Clerk JWT context. A wrong-user cached read would be a
  *security* incident, distinct from iOS's cache purge (a *reliability* problem,
  below).

### 3. MEDIUM — Web Push / install-prompt permission hygiene
- **Our exposure:** if we pursue Web Push (installed Android PWAs see materially
  higher open rates than email — a real retention lever), the documented failure
  mode is **requesting notification/push permission on load**, which gets denied
  and permanently poisons the prompt. Push requires iOS 16.4+ and only for an
  *installed* PWA, and the EU's removal of standalone PWA support shrinks the iOS
  reachable audience further.
- **Action:** gate any push/install prompt behind an **earned-engagement moment**
  (e.g. after a completed Logged Session), never on first paint; feature-detect and
  fall back to in-app cues. **Domain guardrail:** notification copy must never
  become a **daily-streak** nag — ADR-0019 chose a *weekly* Streak precisely to
  avoid pressuring training through legitimate rest days. A "don't break your streak
  today" push would silently violate that decision.

## Implementation References

Curated inputs for upcoming issues. Nothing here is a directive to change code now.

### Market positioning (competitor gaps → our wedge)
- **The universal gap:** across Fitbod / Hevy / Strong / Jefit / Freeletics, the
  2026 reviews agree apps "track what you did and suggest what's next from a fatigue
  model, but **none know how recovered you are right now**." Recovery-aware,
  wearable-integrated coaching is the field's open frontier — and a deliberate
  non-target for us (ADR-0001/0008).
- **Fitbod:** strong equipment-aware strength generation, but a thin complete
  *progression system*, strength-leaning, and now **~$95.99/yr** with a free tier
  that is effectively a 7-day / 3-workout trial.
- **Hevy:** generous free tier (**unlimited logging forever, ~$23.99/yr** paid),
  but a **smaller ~400-exercise library** and **logging-only** wearable
  integration — no recovery data flows into programming. Our AI-enriched catalog
  (invented movements stored once for everyone, `provenance`-flagged) and
  type-neutral spine answer both the library breadth and the modality gap.
- **Freeletics:** good for HIIT, but **not suited to strength/hypertrophy**; adapts
  on **RPE and completion**, not wearable recovery — the "generic after a few weeks"
  critique persists. Our Protocol progression (ADR-0004/0013) + honest PR engine is
  the counter.
- **Pricing/freemium is a live axis:** a ~4x spread between the strength leader and
  the generous logger. Because our gamification is read-time projection, an
  unlimited free honest record is cheap for us to offer — a possible
  differentiator to *state*, not just possess.

### Wearable / HRV trend (the biggest strategic fork — carried forward)
- The fork is unchanged from 07-19: leaders differentiate on **LLM reasoning across
  HRV+sleep+load** and conversationally *explaining* the adjustment; that model is
  inherently **calendar/"today"**-bound and collides with ADR-0001/0008/0018 and
  the read-time-projection rule. Not a drop-in feature — a second product posture.
  See Question 1. The safe, invariant-respecting slice remains: an optional wearable
  signal could **only inform the existing 3-state Readiness** (no recovery %, no
  dated schedule, no "today").

### Visual workout-builder UX (for the ADR-0023 manipulation layer)
- **Affordances:** distinct drag-handle icons; hover state changes the cursor to
  signal draggability; escalating per-state visual feedback through the drag.
- **Touch:** handle/target ≈ **1cm × 1cm** of unused space so mouse *and* touch both
  work — first-class mobile input, not a fallback.
- **Drop zones:** **dotted/dashed borders**, clear structure, a live insertion
  indicator, and — with two targets (reorder vs group-into-superset) —
  **differentiated feedback + foreshadowing microcopy**.
- **Build-path decision:** native HTML DnD API vs open-source library vs no-code vs
  custom, chosen against the **team's accessibility requirement** (keyboard parity).
- **Superset grouping (ADR-0023)** maps to the well-worn "drag an item into a
  container" pattern; the round-major overlay should read as a visible container the
  user drags members into — consistent with the decision that it is *not* a bare
  A/B/C badge.
- **Invariant-safe:** tail-only editability (ADR-0020), typed `Load` entry reusing
  the log form's kind-picker (already done in F4), and **superset suppression for
  Sensitive-Constraint users** enforced in the shared validator (ADR-0023 /
  safety-cache-bypass posture, ADR-0003).

### PWA UX best practices (for `apps/web`)
- **Caching-strategy matrix (adopt as the SW policy if/when we add one):** app shell
  → **Cache First**; API data → **Network First** with cache fallback; images →
  **Stale-While-Revalidate**. For us, authed `/api/*` stays Network First / uncached,
  aligning with ADR-0022's `cache: "no-store"` seam.
- **Performance bar:** target **repeat-load LCP < 1s** once the shell is cached; tie
  every change to **INP / LCP / CLS budgets**; **test on a throttled low-end
  Android**, not a dev laptop. Highest-ROI PWA work — measurement, not redesign.
- **Perceived performance:** **skeleton screens over spinners**; show cached data
  immediately with a **"last updated" timestamp** and a **"refresh content"**
  action; communicate sync status — offline states are meaningful UI, never an error
  page.
- **Installability is all-or-nothing:** HTTPS + registered service worker + valid
  manifest (icons, `start_url`); miss one and Chrome **silently** suppresses "Add to
  Home Screen." Run **Lighthouse's 13-point PWA audit every major release** — but
  note it **doesn't test iOS-specific behavior**, which must be verified on a real
  device.

### PWA on iOS — platform limits that touch our shipped features
- **No Background Sync API** (all iOS browsers are WebKit). Our Live Session posts
  *nothing* until finish (ADR-0012), so we're aligned — but any future "queue this
  log and send when online" must reconcile on **next foreground**, not background
  sync.
- **~7-day script-writable storage eviction** and tight quotas: a paused Live
  Session held only in `localStorage` can be **evicted**, leaving the
  `ResumeSessionBanner` nothing to resume. Mitigations to weigh (design, not
  decided): treat the local slot as **best-effort**, degrade resume gracefully to
  "start fresh," and keep the *finished*-only server-persistence boundary so nothing
  durable depends on the volatile slot.
- **EU standalone-PWA fragmentation:** Apple removed standalone home-screen PWA
  support for EU users at points in the App-Store-regulation churn, so install-based
  features (push, standalone shell) reach a **smaller, region-fragmented** iOS
  audience. Plan copy/UX for the browser-tab fallback.

## Questions

1. **Wearable/recovery posture — the headline strategic call (carried forward).**
   The market's differentiation is still daily HRV/sleep-driven session rewriting +
   conversational "why," and this cycle's reviews confirm *no* major competitor owns
   it yet. Do we (a) **hold the honest self-paced line** and market *that* as the
   differentiator against the "loggers, not coaches / no one knows your recovery"
   field, or (b) open a **bounded, invariant-respecting lane** where an optional
   wearable signal *only* informs the existing 3-state **Readiness** (no recovery %,
   no dated schedule, no "today")? Deserves a grill session + ADR before any issue.
2. **Do we compete on freemium generosity, and do we say it?** The ~4x price spread
   and Fitbod's trial-grade free tier are an opening. Because our gamification is
   read-time projection, unlimited free logging costs no stored ledger. Is a
   **pricing/positioning** posture (unlimited honest record + export) in scope for
   the FO1 welcome/positioning slice (F-C), or out of scope for now?
3. **Type-neutral positioning — narrate the wedge?** Our real edge over
   Fitbod/Freeletics/Hevy is honest multi-modality (cardio/hiit/yoga/mobility as
   first-class, type-neutral XP/Achievements) and a broad AI-enriched catalog vs
   Hevy's ~400. Should the next cycle ship the positioning/onboarding copy that
   actually *says* this (FO1 is still unbuilt), rather than leaving it implicit?
4. **Builder manipulation scope (ADR-0023).** Confirm the first cut ships **both**
   drag-to-reorder and drag-to-group supersets together, with keyboard + touch
   parity and the drop-zone-feedback criteria above as acceptance criteria — or does
   reorder land first and grouping follow? The accessibility bar (and the build-path
   choice it drives) is the same either way.
5. **Do we add a service worker at all this cycle?** Offline/install/push are the
   PWA levers, but each carries the cache-poisoning and permission-hygiene risks
   above. Is a **minimal shell-only service worker + manifest audit** (Cache First
   shell, Network First `/api/*`, no authed caching) in scope, or do we stay a no-SW
   installable-later PWA for now?
6. **iOS local-storage durability for the Live Session.** Are we comfortable that a
   paused Live Session is **best-effort** on iOS (7-day eviction), or do we want a
   design slice that hardens resume (graceful "start fresh" + clearer long-pause
   messaging) before it bites a real user mid-cut?
